## 目标与输入

建立业务事实的唯一权威 SQLite 存储。阅读总览/执行规则/依赖表、B01 source-map、B02 契约、B03 命令。DSH 会话和 memory 继续使用自己的存储，不为格式统一迁移上游数据。

## 文件边界

独占 study/storage、业务 DB 迁移及编号分配。领域逻辑由 C02—C06 实现；后续需要字段时由本任务所有者/集成人统一落实迁移。不得把数据库暴露给前端或生成工具。

## 实施步骤

1. 选择适合 DSH 运行时/Windows 打包的 SQLite 驱动，验证原生依赖/打包约束，记录选择原因。
2. 先按 B02 建立 S1 的目标、资料、任务、时间块、执行/基础变更历史、幂等结果和必要索引/约束，为领域服务提供事务上下文。C04 的正式计划修订、F 的后台作业等随后按受控迁移增补，不以全量未来 schema 阻塞 S1。
3. 实现请求身份去重、期望版本检查和原子提交基础件；明确同请求不同载荷的冲突处理，失败不得留下半份计划。
4. 实现迁移、干净初始化、打开/关闭、写入屏障与快照参与者接口；只承诺本项目已知 schema，不做旧 StudyBuddy 自动迁移。
5. 加入临时库测试：事务中断、重复请求、并行版本、迁移失败、重启恢复、备份冻结/恢复写入；输出表/索引说明。

## 验收

- 全新/已知旧版本库可确定性打开升级；未知新版本库拒绝破坏性写入并给出恢复指引。
- 并发基于同版本写入最多一个成功；重复成功请求返回同一结果，错误不造成重复记录。
- 事务、幂等结果和版本变更一致提交；不会靠前端按钮禁用代替后端防重。
- C02—C06 有稳定 repository/事务接口，H03 能通过参与者接口取得一致快照。
