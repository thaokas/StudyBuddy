# 递进式交付路线：先基础 DSH MVP，再逐步增强

状态：计划，所有阶段均未执行。版本号只是交付代号，不是已发布版本，也不改变锁定的 DSH 上游版本。

## 1. 两条维度：模块分工与交付阶段

原 A—I 文件夹继续表示**谁负责哪块代码**；S0—S4 表示**什么时候交付什么可用能力**。新增 R 类任务负责阶段集成/验收，不将所有模块完成作为首次交付条件。

- **MVP 指 S0**：一份能实际使用的基础 DSH 桌面发行版，不是整个备考闭环。
- 原设计和旧任务里的“首版/第一版”统一指 **S4 完整首版**，不是 S0 的前置清单。
- 未实现的模块不预装/不启用，界面隐藏相应入口。允许明确写在路线图上的“尚未提供”，不允许把 mock、探针或失效按钮当成已交付功能。
- 后续功能仍属于规划范围，分阶段交付不等于删除。与已交付阶段无关的验证失败，只阻塞相应功能线及完整首版，不阻塞更早版本。

35 个既有任务加 4 个阶段任务，共 39 个任务。S0 不等待 B02/B03、学习工作台、记忆、Schedule 可靠性、Creator 沙箱或全量升级系统。

### S0：最小而真实的 DSH 发行版

**必交付**：沿用原生交互和模型链路，至少一个模型适配器真实验证；聊天发送/流式接收/取消与错误处理；会话创建、切换、重启恢复；至少一个安全原生工具调用；附件可选择/传递并准确说明已验证模型能力；插件加载能力经探针验证（探针不进发布包）；独立数据根；能在无开发工具的目标 Windows 环境启动的测试运行包。

**不做**：学习数据库/日程页、自定义规划、记忆提取、跟进、生成小工具、完整前端重设计、自动更新。品牌只做必要辨识；不为美化推迟可运行版本。沿用 DSH 能力但只宣称实测支持，不承诺全插件/全模型兼容。

**质量底线**：Key 不进聊天/日志/包，不默认明文持久化；隔离原 DSH 数据；阻止误接上游更新渠道；重启不丢历史。若原生凭据机制不安全，先做最小受保护/仅会话方案，不把安全债留给后续。用户测试前提供关闭全部进程后的冷备份/恢复说明；不宣称这是运行中一致快照或自动升级。

### S1：先让学习工具在本地可用

R02 增加最小手动目标/任务/时间块录入表单，并将真实 C02/C03/C05 接到 D03。没有 AI 规划也可以开始使用。工作台只启用已实现能力：C04 的正式计划/撤销、C06 成果、E03 任务上下文答疑尚未接入时隐藏相关入口；原生自由聊天继续保留。

版本/幂等、基本冲突提示、计时中断确认、临时/正式进度区分不能推迟。更新前退出全部进程并冷备份实际数据根；未知 schema 拒绝写入。没有统一热备份和自动更新时明确禁用，不假装已具备。

### S2：加入 AI，而不是用 AI 替换本地操作

接入 E01/E02/E03、正式计划版本和 H02 学习导向模型设置。保留 S1 手动录入，D02 是可选的对话引导。风险/授权、容量不足、资料来源、过期草案处理与撤销都随该能力一起交付。后台复盘和相关记忆暂未提供，不需要为此等待 F/G。

### S3：让伙伴具备持续跟进能力

F03/F04 与 F01/F02 可以并行开发，R04 分别验收，再组合。记忆只有在来源、过期、纠正删除、删除抑制均可用时才启用；跟进只有在去重、静默/专注、恢复合并与保存后反馈均可用时才启用。任一支线失败保留 S2 版本，不用无限权限/不可删除的替代品凑功能。

### S4：补齐完整设计与正式交付保障

Creator 只有通过 A04/G01 的隔离验收才默认开放；完整备份只有协调所有参与者才称为一致快照；升级回滚必须恢复匹配应用/数据版本。最终 I04 覆盖设计全部 14 个场景，不能把前几阶段放行当成完整首版验收。

## 3. 开发并行与发布顺序

```text
首个 MVP 关键路径：A01 → A02 → B01 → R01
阶段放行顺序：   R01 → R02 → R03 → R04 → I04

A01 后：A02 优先；A03/A04 可用独立会话提前排风险，但不拦截 B01/R01。
B01 后：R01 做运行包/冒烟；另一会话可推进 B02 → B03。
B03 后：C01、D01、H01 可并行；F01/G01 仅在各自探针通过后可提前开发。
C01 后：C02/C03 并行；D03 可先用 mock 开发；R02 必须换成真实服务。
S2：E01/E02、D02/D04、H02 按依赖并行，R03 只接本阶段能力。
S3：记忆线与跟进线并行，R04 不等待 G/H03/H04。
S4：创建、成果和发行数据保障按原 DAG 推进，I04 最终汇合。
```

发布放行按顺序，开发不必等待上一阶段包发布；只需满足任务硬依赖并遵守文件所有权。但在上一阶段未通过前，不能拿下一阶段工作替代首个可用版本的交付。有限资源优先投入当前阶段关键路径，不强制开启全部未来任务。

## 4. 每次阶段放行共同要求

1. 固定实际提交、DSH/插件/schema/能力清单；由当前提交构建可运行候选包，交付运行方式、已支持功能和未提供项。
2. 原生 DSH 和所有此前已发布能力回归。测试允许 fake model 做确定性覆盖，但至少一个基线适配器的真实冒烟必须有授权和证据；未执行不能伪报通过。
3. 新持久化数据必须有前一版本到当前版本的迁移/重启测试；无损回退依赖匹配旧程序及升级前快照，禁止旧二进制直接打开新 schema。
4. S0—S3 用明确的停止全部进程后冷备份/恢复路径，默认排除凭据并验证恢复；S4 才启用经 H03/H04 验证的在线一致备份/自动更新能力。早期版本不得连上未经验证的更新源。
5. 未交付插件不启用、未交付入口隐藏、产物不含 mock/探针；回填阶段证据与残余风险。严重数据损坏/泄密/越权问题不因 MVP 身份豁免。
6. 阶段任务 DONE 只是该阶段放行；原模块任务 DONE 仍需完成任务自身范围，不因阶段只使用其中一部分而虚报完成。后续增补契约/接线有独立提交与记录。
