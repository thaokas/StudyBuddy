# 开发者操作指南：会话启动顺序与人工验收

读者：负责启动开发会话、合并代码和验收版本的开发者。  
用途：回答“现在先开哪些会话、什么时候合并、什么时候亲手验收、通过后再做什么”。这不是 AI 执行指令，也不是新增开发任务。  
状态：执行顺序说明；以下勾选框均为待验收项，不代表已经完成。

## 1. 最简单的执行方式

采用 **每轮并行开发 → 合并自测 → 下一轮；每阶段产出运行包 → 人工验收 → 放行下一阶段**。

建议保留：

- **1 个集成会话**：维护公共结构、检查任务交付、协调冲突、合并和运行回归。
- **最多 3 个任务会话**：每个会话负责一个任务，完成后关闭或用于后续任务。
- **开发者本人**：决定是否接受技术变更，操作实际运行包并签署阶段验收。

集成会话可以辅助操作，但不能代替你亲手体验产品。不要一次性启动全部 39 个任务，也不要让多个会话直接写同一工作目录。

本指南给出的是便于管理的保守批次，不增加新的硬依赖。熟悉项目后，只要某任务全部前置已合并并验证，就可以提前启动，不一定等整轮结束。精确依赖以 [DEPENDENCIES.md](DEPENDENCIES.md) 为准，阶段边界见 [RELEASES.md](RELEASES.md)。

### 每次启动下一轮前，检查四件事

1. 前置任务有实际提交、测试结果和已知限制，不只是会话回复“完成”。
2. 前置代码已合并到集成基线，新会话从这份最新基线开始。
3. 合并后的类型检查、相关测试和必要启动冒烟通过。
4. 本轮没有未协调的公共接口、数据库迁移、插件入口或锁文件冲突。

普通开发轮次做的是**技术合并检查**，不要求你每轮都完整体验产品。主要的**产品人工验收共 5 次**，分别在 R01、R02、R03、R04 和 I04 交出候选包之后。

## 2. S0：先拿到基础 DSH MVP

这一阶段先串行，目的是尽快得到真正能用的基础版本，而不是为并行而并行。

| 顺序 | 启动的新会话任务 | 完成后检查 |
| --- | --- | --- |
| 1 | [A01 源码与环境基线](00-discovery/A01-source-baseline.md) | 源码/版本明确，终端可用，有实际启动证据 |
| 2 | [A02 基础能力与扩展验证](00-discovery/A02-dsh-extension-spike.md) | 基础桌面、模型、对话和插件能力实测，未来能力缺口单独登记 |
| 3 | [B01 最小发行底座](01-foundation/B01-workspace.md) | 独立数据根、版本锁定、最小工程和构建方式可用 |
| 4 | [R01 基础 MVP 交付](09-incremental-delivery/R01-dsh-mvp.md) | 交出当前提交的运行包、测试证据、备份/恢复说明 |

**这时不要等待记忆、学习工作台或 Creator 沙箱。** A03/A04 可以有余力时提前验证，但不作为本阶段门槛。环境或基础 DSH 无法运行时，应先解决阻断，不能以写完文档代替验证。

### 人工验收 1：基础 MVP

使用 R01 的实际运行包，而非只有开发服务器的页面：

- [ ] 可以在目标 Windows 环境启动，不要求额外安装开发工具。
- [ ] 可以配置已声明支持的模型，发送消息并收到回复。
- [ ] 可以新建/切换会话，取消生成，理解连接失败的提示。
- [ ] 退出全部进程再打开，会话历史仍在。
- [ ] 至少一个已验证工具和附件传递路径可用，能力限制说明准确。
- [ ] 原有 DSH 数据未被污染，凭据不出现在聊天、日志或运行包中。
- [ ] 按说明做一次停机冷备份，并在临时数据目录验证恢复。

**通过后放行 S0，默认再进入 S1。** 不要求此时已有日程、记忆或个性化学习功能。

## 3. S1：加入不依赖 AI 的本地学习工具

先固定契约和测试底座，再并行开发：

| 轮次 | 可以同时启动的任务会话 | 合并后才能继续的重点 |
| --- | --- | --- |
| 准备 1 | [B02 公共契约](01-foundation/B02-contracts.md) | S1 服务、版本/幂等及错误语义统一 |
| 准备 2 | [B03 测试与 mock 底座](01-foundation/B03-test-harness.md) | 真实测试命令、夹具和当前契约 mock 可用 |
| 第一轮 | [C01 存储](02-study-plugin/C01-storage.md)、[D01 前端宿主](03-frontend/D01-shell-navigation.md)、[H01 桌面生命周期](07-desktop-data/H01-desktop-lifecycle.md) | 数据层、前端接入和桌面桥可独立运行 |
| 第二轮 | [C02 目标资料](02-study-plugin/C02-goals-materials.md)、[C03 任务日程](02-study-plugin/C03-tasks-schedule.md)、[D03 工作台](03-frontend/D03-workbench.md) | 业务服务合并；工作台先用 mock 开发是允许的 |
| 第三轮 | [C05 番茄钟](02-study-plugin/C05-timer.md) | 本地计时及中断语义通过测试 |
| 第四轮 | [R02 本地学习版交付](09-incremental-delivery/R02-local-study.md) | 增加最小手动录入，接通真实服务、构建候选包 |

采用这份保守顺序时，先完成 S0 人工验收。希望提速时，B02/B03 可与 R01 的构建验收并行，但公共文件须由集成会话协调，不因此拖延 R01。

### 人工验收 2：本地学习版

- [ ] 不发规划消息，也能创建目标、任务和时间块。
- [ ] 可以拖拽安排，时间冲突有提示，默认只移动选中的时间块。
- [ ] 可以记录部分完成、完成或文字反馈，未勾选不会被当作未学习。
- [ ] 番茄钟能开始、暂停、结束；计时结束不自动完成任务。
- [ ] 睡眠或退出后不虚计学习时长，中断记录需要确认。
- [ ] 无 API Key 或断网时，本地任务、拖拽、进度和计时仍可使用。
- [ ] 重启数据仍在，S0 聊天正常；升级前冷备份和匹配版本回退可复现。

**通过后放行 S1，再进入 S2。** 此时可以没有 AI 规划，但不能用 mock 作为用户实际使用的数据源。

## 4. S2：加入资料导入、对话规划与任务答疑

下面按最多 3 个任务会话安排，避免一次开五个会话：

| 轮次 | 可以同时启动的任务会话 | 合并检查重点 |
| --- | --- | --- |
| 第一轮 | [C04 计划修订](02-study-plugin/C04-plan-revisions.md)、[E01 资料证据](04-agent-tools/E01-material-evidence.md)、[H02 模型凭据](07-desktop-data/H02-model-credentials.md) | 权威计划服务、资料来源和已有模型配置兼容 |
| 第二轮 | [D02 首次使用](03-frontend/D02-onboarding.md)、[D04 对话联动](03-frontend/D04-chat-context.md)、[E02 规划工具](04-agent-tools/E02-planning-tools.md) | UI 与工具使用同一契约，不建立另一份聊天计划 |
| 第三轮 | [E03 任务答疑上下文](04-agent-tools/E03-tutoring-context.md) | 任务/资料/最新计划能进入原生 DSH 对话 |
| 第四轮 | [R03 AI 规划版交付](09-incremental-delivery/R03-agent-planning.md) | 接通真实服务并回归 S0/S1，构建候选包 |

D02/D04 也可以在第一轮有空闲名额时提前开发；E02 必须等 C04 合并可用，E03 必须等 E01/E02 都合并可用。

### 人工验收 3：AI 规划版

- [ ] 提供目标和材料后，可以通过对话修改同一份计划草案。
- [ ] 未确认的草案不会改动正式安排；超负荷时有风险说明，知情后可试行。
- [ ] 资料缺章节/题号、年份未知或无法解析时会明确说明，不伪造内容。
- [ ] 在工作台拖拽后，Agent 读取的是最新安排。
- [ ] 能从任务进入答疑，也能不绑定任务自由聊天。
- [ ] 排不下的剩余工作仍可追踪，而不是堆到明天或用重叠时间假装排得下。
- [ ] 撤销安排修改不会抹去后来发生的学习记录。
- [ ] S0/S1 功能未退化，迁移/冷备份恢复有证据，候选包不依赖 mock。

**通过后放行 S2，再进入 S3。** 不需要等待主动跟进、记忆或个人工具。

## 5. S3：加入主动跟进和轻量记忆

这阶段分记忆、跟进两条线并行：

| 轮次 | 可以同时启动的任务会话 | 合并检查重点 |
| --- | --- | --- |
| 第一轮 | [A03 记忆兼容验证](00-discovery/A03-memory-spike.md)、[F03 提醒](05-memory-followup/F03-reminders.md)、[D05 设置与记忆面板](03-frontend/D05-settings-memory.md) | 候选兼容有证据，提醒与设置接口明确 |
| 第二轮 | [F01 记忆适配](05-memory-followup/F01-memory-adapter.md)、[F04 晚间复盘](05-memory-followup/F04-evening-review.md) | 记忆作用域/删除接口与复盘授权边界 |
| 第三轮 | [F02 记忆提取](05-memory-followup/F02-memory-extraction.md)、[I01 每日闭环集成](08-integration/I01-daily-loop.md) | 提取/删除抑制和实际每日链路分别通过 |
| 第四轮 | [R04 陪伴跟进版交付](09-incremental-delivery/R04-companion.md) | 两条线组合、跨会话/重启验证及候选包 |

A03 如果已提前验收合并，不需要重做；但更换 DSH/候选版本后要补兼容回归。A03 未通过时，F01/F02 暂停，跟进线仍可开发，已经可用的 S2 保持不受影响。

### 人工验收 4：陪伴跟进版

- [ ] 到时未勾选会询问，而不是直接判定没学习；实际完成后不会重复安排。
- [ ] 提醒不重复轰炸，静默、频率和专注延后有效。
- [ ] 晚间只调整剩余量，并展示已经成功保存的变化；容量不足会明确保留未安排工作。
- [ ] 重排时手动修改不会被旧结果覆盖，关闭自动微调授权后会生效。
- [ ] 新会话能使用相关偏好，短期状态到期不会永久使用。
- [ ] 可以查看、纠正和删除记忆，整理旧聊天后不会立即重建被删除内容。
- [ ] 连续数日未打开不补发大量历史通知，离线失败不伪报调整成功。
- [ ] S0—S2 回归正常，包含记忆/墓碑/游标和跟进状态的停机冷备份可恢复。

**通过后放行 S3，再进入 S4。** 不等待 Creator 和完整在线备份系统；在其验证前仍禁用对应能力。

| 轮次 | 可以同时启动的任务会话 | 合并检查重点 |
| --- | --- | --- |
| 第一轮 | [A04 受限工具验证](00-discovery/A04-creator-spike.md)、[C06 成果统计](02-study-plugin/C06-progress-outcomes.md) | 隔离机制真实成立，成果统计口径可信 |
| 第二轮 | [G01 隔离宿主](06-creator/G01-restricted-runtime.md) | 权限桥、命名空间与攻击测试 |
| 第三轮 | [G02 创建流程](06-creator/G02-creation-workflow.md) | 生成/预览/启用/保存/停用/恢复贯通 |
| 第四轮 | [H03 一致备份恢复](07-desktop-data/H03-backup-restore.md)、[I02 记忆与工具集成](08-integration/I02-memory-creator.md) | 多存储恢复一致、工具真实运行及越权回归 |
| 第五轮 | [H04 安装升级](07-desktop-data/H04-distribution.md)、[I03 故障与安全验收](08-integration/I03-resilience-security.md) | 干净环境安装、匹配版本回滚及故障注入 |
| 第六轮 | [I04 完整首版验收](08-integration/I04-release-acceptance.md) | 最终提交重建候选，覆盖全部设计验收场景 |

A04 如已提前通过且版本未变化，可跳过重复验证。若隔离失败，应保留 S3，不将个人工具改成默认无限权限运行来凑版本。

### 人工验收 5：完整首版

- [ ] 个人工具可以预览、保存、重启恢复、停用及恢复上一可用版本。
- [ ] 工具所需数据/权限清楚，技术报告包含真实越权攻击测试；不能仅凭界面正常就认定隔离安全。
- [ ] 日周月成果有记录依据，取消任务不能伪装成全部完成。
- [ ] 多存储备份能够真实恢复，业务、记忆、会话和工具版本一致，默认不包含凭据。
- [ ] 干净环境可以安装运行；升级失败后恢复匹配程序和数据，原学习记录仍在。
- [ ] S0—S3 核心流程全部回归，未测试平台/模型/签名状态没有被写成已支持。
- [ ] [COVERAGE.md](COVERAGE.md) 的 14 个设计场景全部有对应证据，无关键未解决问题。

**通过后才能将候选标为完整首版可发布。** 是否公开发布、签名及使用发布凭据另外确认，人工验收不自动等于对外发布。

## 7. 验收失败、会话冲突与版本记录

### 某个任务没通过

保留复现步骤和日志，交回原任务范围修复，阻塞依赖它的任务；独立支线可以继续。不让后续会话靠猜接口、直接读私有数据库或修改任务状态绕过阻断。

### 阶段候选没通过人工验收

记录候选提交/包版本、具体失败步骤、预期与实际结果。修复后重新构建候选，重跑失败项和相关回归；在通过前，不将本阶段视为已放行。继续使用前一个验收通过的版本。涉及数据回退时使用匹配旧程序和升级前快照，不让旧程序直接打开新 schema。

### 多个会话修改同一个公共文件

暂停冲突修改，由集成会话协调统一落地。尤其关注公共契约、迁移编号、插件注册入口、根构建配置、锁文件及 DSH 核心前端。并行带来的收益不能以共享文件互相覆盖为代价。

### 每次阶段验收只需留下这些记录

- 阶段、日期、候选包版本和实际提交。
- 人工检查结果、测试报告与证据位置。
- 已知限制、未交付能力及发现的问题。
- 备份/恢复及回退到的匹配版本。
- 验收人和结论：通过 / 不通过。

任务状态仍以各任务文件为准，不在本指南另建一套状态表。人工验收结论可附在对应 R01—R04 或 I04 的交付记录中。

## 8. 现在从哪里开始

**先启动 A01，完成后依次 A02 → B01 → R01，然后进行第一次人工验收。**

如果只记住一条原则：**每个阶段先真正用上，再扩大并行范围；开发完成报告不是人工验收通过。**
