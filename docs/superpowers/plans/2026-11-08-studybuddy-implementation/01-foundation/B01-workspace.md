## 目标与输入

先建立支持 S0 基础 DSH MVP 的最小发行工程，不另建业务后端或独立 SDK 前端。阅读总览/RELEASES/执行规则/依赖表、A01 基线及 A02 核心验证。A03/A04 是后续插件的独立门槛，不等待它们，也不把未验证候选锁成默认依赖。

## 文件边界

本任务独占根工程/构建配置、发行 profile、插件入口注册、公共依赖和锁文件。建立 `evidence/B01/source-map.md` 与 `decisions.md`，把 EXECUTION 中的逻辑目录映射到实际源码位置。后续插件任务只提交入口/依赖需求，由集成人统一合并。

## 实施步骤

1. 固定 DSH 及 S0 实际使用的依赖/最小补丁，整理来源许可，区分探针与正式代码；记忆/Creator 候选稍后分别通过 A03/A04 再锁定。
2. 建立独立 profile、应用/数据标识、最小品牌与当前插件清单；关闭上游品牌更新渠道。S0 以原生 DSH UI 为主，不等待学习页面重设计。
3. 验证正式工程的插件加载与关闭能力，探针可作为测试但不进入发布包；建立能力开关，未来插件未安装/未验证时不自动加载。
4. 登记 study/memory/followup/creator/platform 的拟定逻辑目录、负责人及服务/UI 注册约定即可，不要求建齐空包/适配所有后续生命周期。
5. 输出 source-map、当前版本清单、实际开发/构建命令、最小冒烟及补丁重放说明；R01 做基础运行包与放行，B02/B03 可并行准备 S1。

## 验收

- 新环境按文档可启动 DSH 主体和当前已验证插件；用户原有 DSH 数据不受影响，不因缺少 memory/creator 而启动失败。
- 已建立模块有确切路径，未来模块有拟定目录/负责人且标为未实现；公共文件冲突规则可执行。
- 所有业务实现将在插件内，核心前端只承载交互集成；不存在平行 Agent/业务服务器。
- 交付真实 source-map、决策记录、锁定版本/补丁、启动命令和冒烟结果；B02 不再需要猜包边界。
